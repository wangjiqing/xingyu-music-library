# GitHub Pages 实施说明

本项目已经采用静态站点结构。JSON 保存可编辑的条目，HTML/CSS/JavaScript 提供阅读和检索，GitHub Actions 把二者构建成网站并发布到 GitHub Pages。GitHub 官方说明 Pages 提供静态文件托管，因此不把需要持续写入的 SQLite 数据库当作网站后端。[Pages 文档](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 为什么现在不需要在线数据库

目前约千条记录，一次下载目录即可在浏览器完成筛选与名称检索。JSON 每条一个文件，方便审阅、追踪差异与回滚，也方便未来 Agent 提交精确修改。SQLite 以后可以由相同 JSON 生成，供离线查询或研究使用；它应是可重建的查询产物。

网站不会把编辑假装保存到浏览器后就当成共享资料更新。读者使用核对建议入口，维护者使用 GitHub 编辑或本地修改。提交到 `main` 后重新构建和发布。公开网页不持有 GitHub 写入令牌。

有明确的多人实时编辑、账户收藏或音频访问控制需求后，可以增加服务端 API 和数据库。届时需要明确一次性的主数据迁移，不能让 JSON 和数据库同时成为可独立修改的事实源。

## 发布与回退

仓库设置中的 Pages 发布源为 GitHub Actions。主分支每次提交会校验字段与引用、执行回归检查，再构建 `dist/` 并发布。只有 `dist/` 被上传为网页产物。

GitHub 的发布机制需要 `pages: write` 与 `id-token: write`，这里仅在部署任务授予，构建任务只读仓库。[自定义 Pages 工作流](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

发布失败时旧网站通常继续可用，应查看 Actions 日志并修复，不重新创建仓库。内容回退通过撤销对应提交并重新发布。原始 Excel 不作为线上编辑源。

## 对象存储怎么接

目录条目预留 `audio_refs`，当前为空。以后只填资源 ID，例如 `aud-0123456789abcdef`。对象存储的桶名、对象键、凭据、购买信息和签名地址保存在私有资源服务或私有清单中。

关系为“条目 ID → 录音／资源 ID → 对象存储定位”。当前条目仍可能只是未确认身份的资料记录，不能仅靠同名文件自动认定版本。

若要在网页播放私有音频，另设经过身份验证的资源解析 API，临时生成可访问地址，并由对象存储支持相应跨域与范围请求。GitHub Pages 继续只提供页面。没有音频不影响条目存在、检索或核对。

## 已实现与后续工作

已实现：完整导入、稳定 ID、差异标记、专题、基础搜索、筛选、详情、来源定位、资料下载、GitHub 修订入口和自动发布工作流。

新增 Agent 时，先选 10—20 个具体问题，衡量证据质量、误合并情况和每次有效修订成本，再扩大任务量。初始工具优先读写条目文件及提交 PR，暂不需要额外建设通用 Agent 平台。
